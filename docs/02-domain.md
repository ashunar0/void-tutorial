# ドメイン

## ドメインモデル

会員（Profile）、記事（Article）、タグ（Tag）、いいね（Favorite）、コメント（Comment）、フォロー（Follow）。

| モデル | 持つもの |
|---|---|
| Profile | 会員の ID（認証のユーザー ID と同じ）、ユーザー名、自己紹介、アイコン画像の URL |
| Article | slug、タイトル、概要、本文（Markdown）、書き手、タグ、作成日時、更新日時 |
| Tag | 名前 |
| Favorite | 会員、記事 |
| Comment | 記事、書き手、本文、作成日時 |
| Follow | フォローする会員、フォローされる会員 |

**認証のユーザーとプロフィールは分ける。** 認証のユーザー（Better Auth の `user`）はログインのためのもので、メールアドレスを持つ。プロフィールは人に見せるもので、ユーザー名を持つ。記事やコメントの書き手として画面に出すのはプロフィールだけにして、メールアドレスが画面に漏れる経路を作らない。表示名は持たず、ユーザー名で表示する（RealWorld と同じ）。

## ドメインをまたぐ処理

このアプリで置き場所を考えたいのはここ。

| 処理 | またぐもの | 中身 |
|---|---|---|
| 記事の一覧と詳細 | 記事、会員、反応、フォロー | 記事に、書き手のプロフィール、いいね数、自分がいいね済みか、自分が書き手をフォロー済みかを付けて返す |
| フォロー中の新着 | フォロー、記事 | 自分がフォローしている会員の記事だけを並べる |
| 会員がいいねした記事 | 反応、記事 | いいねした記事を並べる |
| 記事の削除 | 記事、反応 | いいね・コメント・タグ付けを一緒に消す |
| 登録 | 認証、会員 | 認証のユーザーを作るのと同時にプロフィールを作る |

「自分がいいね済みか」「フォロー済みか」は見ている人によって変わる。訪問者には常に false を返す。

## 不変条件の置き場所

| 置き場所 | 守るもの |
|---|---|
| DB | ユーザー名・slug・タグ名の重複なし、いいね・フォロー・タグ付けの重複なし、記事削除時の連鎖削除、外部キー |
| アプリ | 書き手本人だけが記事を編集・削除できる、本人だけがコメントを消せる、自分をフォローできない、タグは5個まで、タグ名の正規化 |

## 計算値

| 値 | 決め方 |
|---|---|
| いいね数 | 保存せず、いいねの件数を数える。数と実体を二重に持たない |
| 自分がいいね済みか | 見ている人のいいねがあるか。訪問者は false |
| 自分がフォロー済みか | 見ている人のフォローがあるか。訪問者は false |
| よく使われているタグ | タグ付けの件数を数える |

## まだ決めていないこと

- ドメインごとのコードの置き場所（`src/` の切り方）と、`void/db` をどこに閉じ込めるか。作りながら決める
- 登録とプロフィール作成をどうつなぐか。Better Auth の `signUp` を画面から直接呼ぶと、ユーザー名を一緒に保存する場所がない。候補は (a) 登録の action をサーバーに置き、そこで認証のユーザーとプロフィールを両方作る、(b) 登録後にユーザー名を決める画面を挟む、(c) Better Auth の `user` にユーザー名の列を足す
